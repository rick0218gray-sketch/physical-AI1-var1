## 1. 課題の概要と目的

「右を指してからお辞儀して」のような日本語の指令を、ロボットが実行できる動作の列に変換して実行するシステムを作った。対象はGazebo上のCRANE+ V2アームである。LLMが動作を計画し、動作ごとに学習したACT（Action Chunking with Transformers）方策が関節指令を生成する。言語の理解と低レベルの制御を分け、用意した動作の範囲内で複合的な指令を実行することを目指した。

講義第5回の「テレオペ → 変換 → ACT学習 → 推論」の流れを土台に、次を追加した。

- お手本の自動生成
- シミュレーション時刻への統一
- 周期動作の安定化
- 学習済みモデルの常駐実行
- 言語による計画

AIは、ACTの学習と推論、およびLLMによる計画の生成に使っている。

### 1.1 しくみ

1. スクリプトでお手本の軌道を自動生成し、6つの動作をそれぞれACTで学習する（人手によるテレオペは0回）。
2. ローカルLLM（Ollama上のqwen2.5）が日本語の指令を解釈し、動作の列をJSONで出力する。できない指令は拒否し、曖昧な指令は確認を返す。
3. 学習済みモデルを常駐させた動作サーバが、計画された動作を順に実行する。

### 1.2 結果のまとめ

| 項目 | 結果 |
|---|---|
| 学習した6つの動作 | 各5回中5回成功 |
| 講義の手順との比較（同じモデル） | 講義の推論スクリプト 3回中0回 → 改良した実行器 5回中5回 |

## 2. システム構成と実装範囲

```text
日本語 → LLM（JSON schema制約）→ 計画の検証 → スキル列
   → run_skill.sh → ACT方策 → ROS 2関節指令 → Gazebo / CRANE+ V2

自動軌道 → rosbag → シム時刻で20Hzに変換 → LeRobotDataset → スキル別ACT学習
```

学習した動作は `bow / point_left / point_right / grip / wave / nod` の6つ（お辞儀、左を指す、右を指す、握る、手を振る、うなずく）である。

![学習した6つの動作（それぞれ個別のACTモデルで実行）](figs/fig_skills.png)

計画側は各スキルの説明と既定秒数を読み込み、`status, interpretation, message, steps` を含むJSONの計画を生成する。statusは次の3通りで、未知のスキルや不整合は後処理で検出する。

- `ok`：実行する
- `reject`：拒否する
- `clarify`：確認を待つ

スキルの実行方式は2つ用意した。GPUにモデルを常駐させるサーバ方式と、実行のたびに読み込む単発方式である。

`grip` は腕とグリッパの動作であり、物体の認識や把持の成功までは検証していない。物理的な実機は動かしていない。

独自部分は、お手本の自動生成、変換器と実行系の拡張、言語による計画と評価系である。上流そのままの部分と自作部分の区分、ライセンスの根拠は [来歴](provenance.md) に示す。

## 4. 動作の学習：ACTの改善と定量評価

### 4.1 時刻と観測をそろえる工夫

**時刻のずれ**：Gazeboの実時間比（RTF）は負荷によって約0.92から0.56まで下がった。壁時計の時刻で収集・推論すると、同じ時間でもシミュレーション内の進み方が変わり、方策の時間軸とアームの応答がずれた。そこで時刻の基準をすべてシミュレーション時刻にそろえた。

- 関節状態の header.stamp を使って20Hzに再標本化した。
- 指令の受信時刻もシミュレーション時刻に補間した。
- 推論もシミュレーション時刻で0.05秒ごとに実行した。
- 周期スキルでは、お手本の生成自体もシミュレーション時刻で進めた。

**観測の工夫**：関節角だけでは、動作の開始と終了、往路と復路を区別しにくい。初版では経過時刻と変位dqを観測に入れたが、アームが止まってしまい失敗した。

- 最終版のphase観測は `[t,0,0,0,0]` とし、動作開始の0.25秒前でデータをそろえた。
- 標準偏差が小さいと正規化した値が発散するため、state/actionの標準偏差を0.05 rad以上にクランプした。
- 遅い応答に対応するため、観測状態を0〜8フレーム前にずらすデータ拡張（lag augmentation）を加えた。

**周期動作**：テンポのばらつきと状態への依存で位相がずれた。テンポをほぼ固定し、予測したチャンクの先頭8要素（0.1秒刻みで0.8秒分）を開ループで実行して改善した。

これらは組み合わせて入れた変更である。std clampやlag augmentationを単独で外した比較はしていない。

**集計の方法**

- 件数と時間はログから転記した。割合は件数÷40で小数1桁に計算し直した。
- GPU競合下のLlamaは、120秒のタイムアウト3件を不正解に数えた。
- 平均・中央値・p95は、応答時間が記録された件だけで集計した。正答率の分母40件にはタイムアウトも含む。

**読み方の注意**

- ローカル8GBのGPUには14B/32Bが載らなかった。A100では14Bと32Bの正答数が同じで、14Bの方が速かった。
- ただし、GPUの種類、実スキルかmockか、同時にかかっていた負荷、測定時刻が条件ごとに違う。純粋なモデル能力の順位とは言えない。
- 3Bは同じseed・temperatureでも82〜88%と揺れた。
- 3Bは「前に歩いて」をうなずきと解釈するなど、危険側に誤ることがあった。7B以上の誤りは、確認を返す安全側に寄っていた。
- Codex CLIの100%はこの40件の計画評価での値で、未知の指令やロボットの実行全体での100%ではない。

### 5.2 逐次実行の結果と改善

**待ち時間の短縮**：単発方式では、スキルの開始までに毎回26〜30秒かかった。モデルをGPUに常駐させるサーバ方式にすると待ち時間は約1秒になり、1動作の所要時間は約40秒から約10秒（bow全体で10.6秒、動作そのものは約9.5秒）に縮んだ。

**手を振る動作の失敗**：常駐サーバにつないだ試験で「左を指差してから、手を振って」を実行すると、point_leftは成功したが、waveは失敗と判定された（2回目の振りが足りない）。

**原因**：調べると、連続実行そのものの問題ではなかった。v3のwaveは、2回目の正側の振れが過去18回とも+0.30〜0.35 radで、成功判定の閾値（0.3 rad超）すれすれだった。サーボの遅れで振幅が出ない回に、閾値をわずかに下回っていた（18回に1回程度）。

**対策**：閾値は変えず、waveのお手本を「ゆっくり・大きく」（テンポ2.0〜2.1倍、振幅0.7〜0.9）してシミュレーション時刻基準で40エピソード集め直し、v4として再学習した。

| 項目 | v3 | v4 |
|---|---|---|
| 2回目の振れ | +0.30〜0.35 rad | +0.53〜0.55 rad |
| 成功条件を満たすお手本 | 34/40 | 40/40 |
| wave単体 | 5/5 | 5/5 |
| 常駐サーバ経由の連続実行（point_left→wave、bow→nod、grip→wave 各5回） | 各ステップ15/15 | 各ステップ15/15 |

修正前の30回の連続実行でも失敗は再現しなかった。そのため効果は、成功回数ではなく閾値との余裕（約0.2 rad増）で示す。試行数は少なく、逐次実行全体の成功率を統計的に示したものではない。

**デモ動画で確認した動き**（[demo_nl_commander.mp4](../crane_act/videos/demo_nl_commander.mp4)、36.8秒）：

- 「左を指差してから、手を振って」：2動作を連続で実行した。
- 「コップを取ってきて」：確認（clarify）と判定され、動作しなかった。
- 「歌を歌って」：拒否された。

**残っている課題**：「右を指してから、5秒間お辞儀して」では、計画したbowが5秒の指定を反映せず6.2秒になった。短い指定で学習済みの動作を途中で切らないよう、実行時間に既定秒数の下限を設けているためである。また、終了コードは動作の成否と関係なく0を返す。動作の失敗をコマンダー側で検出し、停止して報告する改善の余地がある。

## 6. 考察と今後の改善

**モデルと実行系は分けて調べる**：次のような問題は、モデルを大きくしても解決しない。収集・変換・推論の時間の基準を統一したことが、再現性の土台になった。

- シミュレーション時計の滞留
- RTFによる時間軸の不一致
- joint3/joint4の並び
- ほぼゼロの標準偏差

**学習データ上の誤差だけでは成否を判断できない**：phase観測とchunk実行で周期動作は改善したが、同じ直立姿勢からの動作に合わせた結果であり、姿勢がずれると失敗が残る。今後は、開始姿勢のランダム化、事前に固定した判定基準、独立した試行で評価する。

**JSON schemaだけでは意味の正しさは保証できない**：構文やスキル名は制限できても、指令の意味が正しいとは限らない。大きいモデルでも、曖昧な文脈の補完や余計なスキルの追加が残った。意味の検証を強め、動作が失敗したら止めて利用者に報告し、範囲外の指令は確認に戻すべきである。「さっきと同じ動きを」のような文脈が要る指令には、会話の履歴を計画に渡す必要がある。

**実用性と評価の範囲**：常駐化による待ち時間の短縮は、対話的に使ううえで効果があった。一方、今回の評価はシミュレーションと少数の定型動作に限られ、物体認識、環境に応じた経路計画、実機での接触の安全性は扱っていない。計画・個別スキル・逐次実行の各段階を別々に測り、未知の指令や外乱を増やして評価することが次の課題である。
